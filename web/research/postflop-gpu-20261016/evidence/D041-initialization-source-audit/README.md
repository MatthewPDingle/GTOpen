# D041: initialization source audit

Source-only, accepted E020 baseline; E022 remains a separate fixed experiment. No source change, compiler, GPU, profiler or new benchmark run. Recommendation: do not implement a PTX cache as the next2%-gate candidate. A more credible but unmeasured lead is the large compressed-arena positive-zero proof; isolate its CPU cost before proposing an optimization.

## Cache and constructor boundaries

`gpu/mod.rs:208-223` builds one GpuPlan, computes admission, and reuses that plan for upload. `225-237` acquires the primary context/stream and device architecture. `239-252` already uses a process-local static OnceLock<Result<Ptx,String>>; the first constructor compiles included kernels.cu for compute_CC using default NVRTC options, subsequent constructors clone the cached PTX/result. `253` loads a separate CUDA module for each solver. No application disk-PTX cache is present in this path. The inspected cudarc0.19.7 `nvrtc/safe.rs:116-122,146-166` creates a program, invokes compilation and extracts its PTX image; `driver/safe/core.rs:2173-2203` separately loads that image into the context. Warm driver cache therefore does not establish that runtime NVRTC compilation was skipped. The process cache avoids repeated calls within one process, while each fresh benchmark process starts its static empty.

Context retention already exists for the server's VRAM-query path: `gpu/mod.rs:1107-1112` retains MEM_CTX, and `server/main.rs:355` calls it for sizing. Blindly retaining another context to improve fresh-test initialization could be application-irrelevant and shift destructor work outside the primary boundary. Any future lifetime change needs external process/end-to-end evidence including teardown, not just the frozen score. The architecture string is built before the OnceLock on every constructor; its tiny allocation is not a credible complete-cycle target.

`mod.rs:263-275` creates one pinned staging buffer/two arena layouts and uploads four learning stores. `arena.rs:81-100` first validates scale bits are exactly+0, then serially OR-reduces every I16/U16 q word; the snapshot/sentinel checks also must pass. `arena.rs:107-112` already uses the accepted E004 device-zero shortcut, skipping host f32 decode and host-to-device copy when the proof succeeds. Otherwise full/warm/compact/F32 paths remain at114-175. Each zero shortcut still allocates/clears a device buffer and waits; the existing diagnostic group includes all of those operations. `mod.rs:311-374` subsequently looks up functions, uploads immutable metadata and allocates work buffers.

## What timing evidence actually supports

D009 and D009R2 are historical E004-era host-boundary diagnostics, not a fresh E020 isolation. Their first PTX acquire/compile spans are57.8602 and61.5325ms; later fixtures are0.0221-0.0257ms. The D012 constructor diagnostic on rejected quantized-readback source similarly reports55.9444ms first,0.0262/0.0306ms later. These spans surround PTX get-or-init plus clone and associated NVRTC setup; they do not separately time only nvrtcCompileProgram or driver JIT. Module load has a distinct roughly1-2ms span. Timers/logging perturb all three diagnostics. D012's river CPU-plan outlier87.2595ms versus D009R2's0.035ms is a warning against attributing broad constructor differences without a split measurement.

Recent preserved E020 controls B068/B069/B070 sum to9773.6231ms of fixture medians;2% is195.4725ms. For scale only, eliminating the entire historical61.5325ms first PTX span would correspond to0.6296% of that recent total. This cross-source/cross-cohort ratio is not a measured E020 bound or expected gain, but it supplies no evidence that a disk cache can reach the gate. Such a cache would additionally require content/compiler-version/options/architecture invalidation, atomic writes and failure handling, and would not remove module loading.

The D009R2 arena-upload groups total388.1660ms (3.9716% of the recent total for scale only). This is the only inspected constructor group with enough apparent headroom to justify a small follow-up. It does **not** establish that the q scan consumes that time: zero proofs, CPU page/cache behavior, allocation, asynchronous memset and existing waits are still mixed. The plan group is about237ms and pinned-allocation group111ms in that same old run; total removal is impossible, and those figures are not transferable current savings.

## One evidence-gated lead

Potential next change, only if isolation supports it: parallel chunked integer OR for large compressed q arrays in can_upload_zeros, retaining the scale-first gate, exact u16 cast/OR criterion, empty-array result, small-array serial path and all existing snapshot/F32/warm fallbacks. Integer OR is associative with zero identity, so its parallel grouping need not change any floating operation or source arena bit. Read-only ArenaBuf::as_slice requires no concurrent traversal (`store.rs:58-60`), unchanged by parallel readers. Rayon is already available; Spot's flop/turn table construction uses it (`game.rs:469,497`), but actual pool/cache/page state and memory bandwidth still need measurement. This extends the accepted E004 proof scan; it is unrelated to rejected quantization/readback encoders E009-E013. No threshold or implementation has been selected.

A narrow opt-in host trace around scale validation, q OR, device alloc/zero and the existing wait would answer the unresolved split without adding CUDA waits or touching frozen evaluator bodies. Compare against the ordinary complete cycle and preserve all diagnostic outcomes. If the measured scan has less than roughly the required saving or parallel startup/bandwidth costs erase it, stop. Do not skip the proof based on solver.iteration==0: loaded or externally modified stores can have nonzero, signed-zero or nonfinite state. No cache, context-lifetime, wait-removal or parallel-scan change is authorized by this note.
