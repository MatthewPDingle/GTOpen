The PTX `applypriority.global.L2::evict_normal` instruction provides an explicit scoped normalization route. This narrows the D063 hold; it does not authorize a production candidate or establish speed. The original report remains sealed.

Use the actual aligned allocation base and only `floor(bytes / 128) * 128` bytes of immutable `d_cfv_slot`: 5,387,136 bytes (42,087 lines) for either retained flop plan, or 128 bytes for river. Read back the stream/captured-node attributes and require exactly that owned window. Do not round outside the allocation. Existing-reservation eligibility is checked in the actual solver context; no global reset or limit mutation is allowed.

The instruction requires aligned global addresses, 128-byte operations, PTX7.4 and SM80+. CUDA12.1.1 documents a prefetch for absent lines, so cleanup may generate substantial traffic. The unsupported async.bulk form and destructive discard are excluded. See the [archived12.1.1 PTX contract](https://docs.nvidia.com/cuda/archive/12.1.1/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-applypriority) and [archived13.0.3 contract](https://docs.nvidia.com/cuda/archive/13.0.3/parallel-thread-execution/index.html#data-movement-and-conversion-instructions-applypriority).

A clean/dirty epoch can retain captured graphs. Before any fallible hinted submission, mark potentially dirty; before normalization, stop submissions, drain work and disable the stream policy. Normalize every owned line, then synchronize before marking clean or freeing. Existing graphs can reintroduce persistence only in a deliberate later dirty epoch. Stream disabling does not erase their captured attributes. Constructor errors, partial submissions, lock recapture, continuation and explicit close/Drop fallback need the same ownership discipline.

Successful full `sync_to_cpu` must pay normalization and completion before returning. The frozen evaluator stops its readback/total timers afterward (lines232–236), so this places cleanup inside the existing score without editing the harness. Destructor-only cleanup would hide a new cost. No actual cleanup latency or benefit is known.
