# Down-to-up sigma cache: source-only feasibility review

**NO-GO for immediate implementation.** The lifetime is feasible and the proposal is distinct, but the straightforward design introduces a large persistent allocation and extra global traffic without evidence that it has worthwhile complete-cycle headroom. This is a prioritization judgment, not a proof that caching cannot improve a future measured workload. No implementation, harness, compiler probe, native run or GPU work was performed.

## Exact lifetime and arithmetic

`kernels.cu:73–91` computes each actor's regret sum, normalized probability and child reach. `:373–396` recomputes the same sum/probability before that actor's upward regret/strategy update. Action blocks are disjoint (`plan.rs:368–375`) and the up pass only writes the traverser's learning arrays (`mod.rs:975–976`). Earlier updates of descendant nodes do not change a parent's own old regrets. A separately allocated, correctly indexed f32 cache can therefore retain the pre-update sigma without aliasing learning, reach or CFV storage.

E015 is essential: ordinary p0 down is full; immediately following p1 down passes nh1=0 (`mod.rs:763–820`). Thus cache1 must be filled during p0 down and retained through p0 up and p1 down until p1 up. Up0 changes only regrets0, so old actor1 sigma is still current. P1 down must nevertheless compute actor0 reaches from updated regrets0. Do not reuse stale actor0 sigma for those reaches, require p1 down to refresh actor1, or infer validity merely from p==1. Both player caches must coexist; aliasing them to one max-sized arena would overwrite probabilities before consumption.

Preserve the positive-part ternary, ascending +0.f sum, threshold `sum > 1e-12f`, division, action accumulation order and original update expressions. Down's uniform reach is **pr/na** (`kernels.cu:81,89`); up's uniform sigma is **1/na** (`:379,383,393`). Cache the latter separately while retaining pr/na verbatim. Recovering sigma from child_reach/pr fails at zero reach and changes rounding. Keep locks on the existing lock_sigma path (`:57–68,355–365`); locked cache slots may remain unwritten only if never read. Storing an already rounded f32 sigma does not itself change its bits, but changing the kernel can change compiler association/unrolling/FMA decisions. Source equivalence is not bitwise runtime proof, including threshold/subnormal/signed-zero cases.

## Lifecycle and integration cost

- Full p0 down then up0, partial p1 down then up1 is already queued on one stream in eager, profiled and captured modes (`mod.rs:393–449`). No new graph variant or cross-iteration validity flag is inherently necessary if every full first-down/standalone sweep overwrites the needed cache before use. Allocate fixed buffers before capture; warm resumed construction may capture on its first iterate. Do not depend on an eager warmup.
- Evaluation uses the same down entry with **strategy sums**, then separate eval-up (`mod.rs:545–589,731–744`). Disable cache writes there or overwrite completely before the next training consume; never substitute regret sigma into eval-up. Ordinary lock updates invalidate graphs (`:1046–1057`). Error retries must start at a full producer before consuming old scratch.
- Generic continuation always uses a full single sweep (`mod.rs:178–194,759–760`), so arbitrary p/root order can regenerate its own sigma. Symmetric continuation then projects/transports learning arrays (`continuation.rs:119–150`); never reuse prior scratch after that mutation.
- Existing paging/stored workspaces move exactly seven large mutable buffers (`continuation_paging.rs:10–55`; `continuation_storage.rs:93–139`). Leaving two new cache arrays resident per board would defeat their resident-memory design. Either expand their workspace/length/swap/absorb and poison/error accounting consistently, or deliberately disable this optimization there with an accounted policy. They must not silently accumulate unreported per-game GiB.
- Budget accounting must include actual cache payload in full and compact admission (`mod.rs:213–220`), conservative UI estimate (`game.rs:419–421`), and planned/observed retained-versus-workspace continuation accounting (`continuation_capacity.rs:27–81`). It cannot hide inside the 512 MiB reserve. Full F32 arena selection changes node offsets, so cache lengths/indexing must use the finalized layout.

## Cost and evidence

For finalized arena lengths A0,A1 the simple cache costs **4*(A0+A1) bytes**, 50% of the existing 8*(A0+A1) regret-plus-strategy payload. Retained B083 whole-arena fingerprints imply 1,364,772,032 bytes (1.271 GiB) for non-isomorphic rainbow and 32,832 bytes for river; two-tone's full-layout upper bound is 1,369,522,280 bytes (1.275 GiB), while its compact allocation is smaller and was not measured here. At least one extra f32 cache write and read per cached element is introduced. Up still needs original regret values for discount/update, so this is not elimination of all regret reads. Cached writes during the second down may be avoidable, but only with explicit producer selection preserving the above lifetime. These are payload/logical-operation observations, not memory-transaction, kernel-time or performance estimates.

D038 README line25 screened out an **intra-up** cache because compiled common NA2/3/4 code already shares normalized registers between value and strategy updates. It does not evaluate this cross-kernel cache. Scoped current design/patch/ledger search found no duplicate postflop experiment. Older `research/autoresearch/results.tsv:686–721` documents **preflop** E021/E021R removing a full sigma arena, reducing memory and measured iteration times; that is relevant counterevidence about the traffic tradeoff, not a postflop rejection or current-hardware prediction. D045 selected-event samples establish no native whole-solve share or >=2% headroom.

If reconsidered later, use immutable-original raw-device and CPU-state comparisons through complete pairs, both algorithms/storage layouts, nonuniform/zero/threshold regrets, zero reaches, locks, arbitrary menus, graph/profile/eval/warm-resume transitions and continuation workspace/root changes. Capacity tests must verify planned and observed payload plus exact-budget boundaries. Existing compressed primary fingerprints alone cannot qualify this architectural change. No new test or probe is recommended before a stronger cost rationale; retain this as a source-feasible contingency behind smaller bounded candidates.
