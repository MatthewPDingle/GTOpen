# Attribute the next larger pilot's runtime

The failed 112-board pilot did not report progress between checkpoints, so it cannot distinguish training time from final evaluation time. Before another large run, add a separate research-example-only timing change. Leave solver state, update order, CUDA calls, board weights and mathematical operations unchanged. Log construction completion, each completed training iteration, and the beginning and completion of each evaluation. Accumulate setup, training and evaluation wall times in the existing checkpoint output. Do not add GPU synchronization calls or use these measurements as kernel-only timings.

Prepare the change outside the running source. After storage changes are qualified, compile it separately and require identical scientific output at 1 and 20 on the existing three development boards against the retained reference. Timing fields are explicitly outside that numerical comparison. Keep the ordinary production-idle guard and resource/time limits. A later large run must have its own registered scope and deadline; timing instrumentation does not authorize extending the failed run or treating a short profiling probe as a converged solution.
