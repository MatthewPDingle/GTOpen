Resource arithmetic and what it does not establish

At the original two board/three physical workers, at most six native processes
overlap within one context: two boards, three physical workers, one parent
bridge-query exporter. Native declared output totals4,256,000,000 bytes at2GB
per board/64MB otherwise. The physical workers can also produce up to192MB of
retained river JSON copies at once. Thus4.448GB is a useful active native/copy
envelope, not a total store or RAM bound. Up to six physical results are pending
for ordered admission; finished results and event dictionaries remain in RAM.
The other four contexts do not run concurrently.

Resource-only alternatives preserve draw/order/math: one board/two physical
workers with the same board cap gives2.192GB native plus128MB duplicate envelope.
An explicitly registered256MB board cap gives768MB native+192MB copies with2/3
workers, or448MB native+128MB copies with1/2 workers. Such a tighter cap is a
prospective failure condition, not a guarantee deeper-stack boards fit it.
No unattempted launcher or new cap has been applied.

The proposed generation contains10 board exports,65 physical batches and65 each
of query/verify/trace exports. Conditional river chunk count is data dependent.
The very loose query_limit1m bound allows31,250 chunks/batch and4,062,500 river
exports. The resulting raw-native-plus-retained-copy ceiling is520,032,480,000,000
bytes at the original caps, even before derived files. This loose finite bound
demonstrates that per-invocation caps alone cannot guarantee an800GB whole-study
ceiling or predict a successful five-stack run. It is not an expected workload.

Specified array sizes are smaller: ten512-row weighted reservoirs total701,440
bytes; five cumulative preflop array sets304,200 bytes; maximum fit rows per
actor4926/4250. Width362 implies14,580,960/12,580,000 bytes for host float64
features+targets+weights, and7,290,480/6,290,000 CUDA float32 bytes. These exclude
staged/restored copies, grouping temporaries, Python/Rust trees and dictionaries,
models/Adam/graphs/allocator/runtime, inference caches and queues. The9,348,488
matrix figure in resource-arithmetic.json is hypothetical dense1081x1081 float64
arithmetic, not evidence that the current sorted-terminal reducer allocates one.
Neither the20GB free-RAM guard nor an output byte cap is a total memory quota.

Concrete derived writers and minimal prospective I/O controls

sampled_physical_root_evaluation_v1.save is imported into pipeline/river worker,
and passed as transport.generate(write=save). It writes source-generation.json,
batch.json, policies.json, collection.json, metrics.json, worker-result.json;
derived-targets/postflop-targets/weighted-targets/river-targets/ordered-events;
and conditional requests/process/evidence/overlay JSON. It currently opens the
exclusive file BEFORE json.dumps. Board worker _save writes request/result JSON.
Native execution _write writes success/failure process receipts. The launcher
write writes registration/attempt/result/failure/release. Checkpoint objects use
sampled_visible_hybrid_checkpoint_v1.encoded and publish: publish writes .partial-*
then renames to a content-addressed destination and verifies existing conflicts.
Do not change this object's bytes, hashes, duplicate/conflict semantics or RNGs.

Transport directly copies <=64MB native stdout to each *-native.json and writes
policy arrays via np.savez_compressed. The native river query gate bounds history
and selected rows to250,000 each, four float64 probabilities per row: combined
array payload<=16MB per policy npz;17MB is a conservative proposed file bound
including ZIP/NPY overhead. A worker performs one such write at a time. Three
simultaneous physical writers would add at most51MB if this file bound is enforced.
Checkpoint reservoir NPZ calls also bypass JSON save and need coverage.

A minimal RESOURCE-ONLY prospective layer should check serialized length and
admission BEFORE open/first write, preserve exact original JSON separators/key
order/newline bytes and atomic checkpoint semantics, cap streaming NPZ/raw writes,
and enforce that every destination is a new ordinary file in the new owned store.
Keep a small separate reserved failure/receipt/release budget so a resource refusal
can still retain its bounded diagnostic and cancellation witnesses. Native direct
outputs already use declared argv roles/create_new; do not reinterpret them.

For example,64MB per ordinary derived write and1MB per receipt/diagnostic are
candidate resource limits, not selected parameters or demonstrated sufficient
sizes. At2/3 workers, six Python processes can each serialize/write one derived
artifact (two boards, three physical, parent); this adds up to384MB, plus up to6MB
receipt allowance. Combined with native/copies/51MB NPZ, the illustrative envelope
is4.889GB. Adding envelopes is deliberately conservative; it is not total RAM or
a hard disk quota, and ordinary Python objects exist before serialization.

Calling the old guard before a write is insufficient if its storage measurement
is still throttled for3 seconds: a process can finish many writes between scans.
Either perform the storage check at every admitted write or use an atomic shared
logical-byte reservation/counter across ALL parent and spawned writers. Reserve
each native operation's declared aggregate cap before launch; replace reservation
with retained actual bytes after terminal verification without dropping failed
artifacts. Reserve derived serialized length before open. Include temporary
checkpoint bytes, raw duplicates, NPZ and diagnostics. Parent-only monkeypatches
do not carry into spawn: install the same declared resource layer in child
initializers, and pin/check the extra implementation and its configuration.

Per-write caps plus unthrottled guarded accounting close most derived disk burst
risk. A shared pre-write reservation cap gives a logical allocation acceptance
contract. NTFS allocation and volume free-space remain separate sampled checks;
none of this is a filesystem quota. Checking len(json.dumps(...)) after building
the document also fails to bound decoding/construction/serialization peak memory.
Bounded streaming encoding can cap the serialization buffer, but actual Python/
Rust object construction and deeper topology remain an explicit memory gap.
Do not implement a new poker evaluator or alter target/inference/retention gates
to make a resource check pass. A refused attempt is retained and cannot retry.
